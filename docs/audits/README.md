# Device types: their one reference and how far we follow it

The rule (see `CLAUDE.md`): ONE best-maintained working reference per device, followed to the
letter, proved by an audit + checker + a test per row. Status as of 2026-11-10.

| # | Device / link | The one reference | Audit + checker | Status |
|---|---|---|---|---|
| 1 | Prusa MK3/MK3S family (agent, serial, `--mode prusa`) | PrusaLink + Prusa-Firmware | [prusalink.md](prusalink.md), checker green | **53 identical, 95 differs**, 16 n/a, 2 open (by reading both sources). Polling on PrusaLink's schedules in every state (idle, paused, printing, attention, error; 1 / 10 / 30 s, measured against PrusaLink itself 2026-11-12); retry after an answer that did not do and the job id read-back as PrusaLink's; still to do: start-up order, start-up order, line numbering, message parsing |
| 2 | Prusa Buddy (MINI, MK4, XL; Prusa Connect protocol to the hub) | Buddy firmware 6.3.0 + master | [buddy.md](buddy.md), checker green on coverage | **349 rows UNCHECKED**, 1 OPEN |
| 3 | Klipper (Moonraker to the hub) | Moonraker | [klipper.md](klipper.md), checker green on coverage | **281 rows UNCHECKED**; 6 items we send/read are not Moonraker's (named in section 6) |
| 4 | Plain Marlin (agent, `--mode marlin`) | OctoPrint 1.11.8 @ `42be740` (with its own virtual printer as the test device), run on CPython 3.13.12 | [octoprint-marlin.md](octoprint-marlin.md), `scripts/octoprint-port-check.py` | **22 of 24 scenarios identical in 5 of 5 runs** (22 frozen + 2 added), none differs; 2 are not compared because OctoPrint's own code differs between its own runs (`connect_auto`: `N2 M21` or `M21`; `emergency_m112`: whether the monitor reads the printer's echo). OctoPrint's own `Printer`/`MachineCom` and our port, both against OctoPrint's virtual printer, bytes written and lines read compared; the reference over the same out-of-process bridge writes the same. `Thread.start` follows the GIL's order by an approved approximation (ours, listed in the audit). Not tried on a real printer; the old `marlin.md` stays |
| 5 | GRBL lasers (agent, `--mode grbl`) | LaserFoundry v0.5.0 (`61febdb`): `laserfoundry-device`, `laserfoundry-gcode`, and its app's link logic (`ui-egui`) | [laserfoundry-grbl.md](laserfoundry-grbl.md), proof in `crates/engine/src/ports/laserfoundry/proof.rs` (no checker script) | **Bytes identical** in 13 scenarios (connect, controls, typed line, job, frame, pause/resume, stop, start again from a line) between LaserFoundry's own `Link` driven as its app drives it and our port, on LaserFoundry's `SimulatedGrbl`; the `?` polls counted apart. LaserFoundry's own tests pass (71 + 49 + 292). The link logic (reconnect, refusals) has the app's own cases as tests, not compared by a run of both. Not tried on a real laser or serial port; Marlin and Smoothieware lasers closed; the frame's whole chain from the hub is not run in one test (G4) |
| 6 | DYMO LabelManager PnP (agent, USB, `--mode dymo-pnp`) | labelle @ `5e8f1e5` (with pyusb 1.3.1, Pillow 12.3.0) | [dymo-labelmanager.md](dymo-labelmanager.md), `labelle-port-check.py` | **52 of 52 examples identical** (labelle's own command line, real pyusb and Pillow, against the Rust port: finding, string reads, opening, every transfer, picture to bytes, closing, errors) and **30 of 30 constants and command bytes identical**. Nothing sent while idle, as labelle. The `nusb` stand-in is not yet tried on the printer |
| 7 | DYMO LabelWriter 450 (agent, USB, `--mode labelwriter-450`) | DYMO's own CUPS driver 1.4.0 (`raster2dymolw`, `lw450.ppd`), with CUPS 2.4.20 (`ef80eea`) as its runtime | [dymo-labelwriter-450.md](dymo-labelwriter-450.md), `scripts/dymo-labelwriter-450-check.py` | **14 of 14 cases identical** (the real `raster2dymolw` built here and the port, on the same pages: stdout bytes, stderr lines, exit status; the three halftonings, the sizes, density, quality, resolution, continuous) and **61 of 61 `PageSize` headers identical** (CUPS's libcups on the real PPD vs the port); the driver's own tests: 24 of 26 cases ported and passing (2 are the Twin Turbo's); every function of the ten driver files is ported or listed as not ported (146). Not tried on the printer; the `nusb` stand-in for the `usb` backend is untried. Not covered: Turbo, DUO, Twin Turbo, LabelManager, the status flow of a paper-out against the real filter, the hub's picture size and orientation |
| 8 | Spoolman API (Moonraker `[spoolman]`, OctoPrint plugin, Mainsail/Fluidd talk to the hub) | Spoolman @ `eccb05e` | **none** | **Unchecked.** Built from reading Spoolman, not proved. The UI may be our own (user decision); the API and data must be Spoolman's to the letter |
| 9 | Virtual machines (hub simulator) | n/a (ours, for tests and demos) | n/a | n/a |

## Not covered

- Label layout on the hub's side (what the hub draws into a label's PNG, including its own 16 mm
  trailing blank): ours, not protocol. The margins labelle adds to a picture are in the port and
  covered (row 6).
